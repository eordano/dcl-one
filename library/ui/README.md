# @dcl/one-ui

Shared UI foundations and components for dcl-one, and the Node-only Figma tooling that generates the foundations and the Review previews.
The standards they follow are in [`docs/ui-standards.md`](../../docs/ui-standards.md).

The [component adoption tracker](../../docs/ui-components.md) links the authoritative local contracts, pending work and verified application adoption. Update it in each PR that adds a public component or migrates a consumer.

| Path                   | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `figma/`               | Node-only: CLI and MCP server (`dcl-figma`), Review gallery (`review/`), consumer skill kit (`agent-kit/`), `key-guard.mjs`, `lock-digests.mjs`, `port-verification.mjs`. Never imported by browser code. Maintenance notes: [`figma/MAINTENANCE.md`](figma/MAINTENANCE.md).                                                                                                                                                                                               |
| `components/`          | The shared components, hand-written (one directory each: component, styles, tests, Code Connect mapping) or promoted from the capture (`promotion.json`), exported from `index.ts`.                                                                                                                                                                                                                                                                                        |
| `templates/component/` | Starting point for a new shared component.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `apps/hud/`            | The Explorer HUD UI its two hosts share (`rendering/bevy-explorer/source/react-web` and Sites' `apps/ui3/src/play`), imported as `@hud/*`. It keeps the HUD's conventions: its hosts type-check it, and lint and formatting here skip it. `react-web` runs all its tests, and `apps/ui3`'s `play-shared` project runs them against `/play`'s host; the `hud` Vitest project here runs those that need no package only the hosts install (all but `apps/hud/test/hosted/`). |

## Shared foundations

The public `@dcl/one-ui` entry exports colors, icons, typography, responsive layouts and spacing, including semantic CSS references through `theme`. Load `@dcl/one-ui/foundations.css` once from the consumer's global stylesheet; it provides the shared CSS variables and bundled Inter fonts. Import typography classes from `@dcl/one-ui/text-styles.module.css` as a CSS Module. The browser entry also exports the hand-written NavBar; the CLI stays Node-only.

Consumers that only need tokens or icons use the public `@dcl/one-ui/foundations` entry. The Explorer HUD uses that entry so components are outside its compiled and fingerprinted source closure. Its checked shared-input manifest is generated from the actual HUD compiler and web/native Vite graphs, including CSS processor dependencies and assets; source selection, artifact fingerprints, dev access, native staleness and Nix consume that same contract. The root entry also exports the hand-written NavBar. Vite/Vitest configuration reads structurally safe manifest paths during local iteration; strict source-byte validation remains in the explicit graph check, CI, artifact acceptance and Nix. Validated edits to existing owned HUD source bodies use modification times against the last successful local bundle, so unchanged repeated runs reuse it; structural, resolver or shared-input drift still requires regeneration, and malformed or unsafe metadata aborts; loading configuration never regenerates the graph. Strict CI planning and artifact acceptance require manifest regeneration after every edit, addition, deletion or rename under the tracked HUD `react-web/src` roots, even a comment-only edit, and after changes to `app.html` or `index.html`. Bridge-scene, web-engine and other owned files become manifest controls only when reached by the actual compiler or Vite graph; changes to those recorded controls, shared imports or resolver scopes also require regeneration. Unreached owned files retain the separate Explorer source fingerprint. Run `npm --prefix rendering/bevy-explorer/source/react-web run gen:shared-inputs` from the repository root with locked dependencies and canonical Rust-generated bindings.

The HUD graph refuses CSS Modules composition (`composes` and `compose-with`) because Vite's current PostCSS Modules pipeline does not report those file dependencies. Supporting composition requires upstream dependency reporting; this contract does not attest to arbitrary CSS processor reads. Inline PostCSS plugins remain part of the actual pipeline; automatic or external PostCSS configuration is refused instead of silently replacing it. Filtered source archives without Git validate the checked manifest against regular physical files and the complete HUD root inventory before use.

The HUD schema 2 contract also records names and regular-file/directory kinds in actual shared-input ancestor directories, without hashing unused bodies. Candidate-name additions, deletions or renames require regeneration; new untracked candidates and unsafe entries are refused. Git checks exact namespaces; Nix checks the original source before filtering, and filtered archives allow only the expected subset with all selected identities required. Historical schema 1 bases rebuild conservatively; current heads migrate through the canonical generator.

NavBar and its prop types are exported from `@dcl/one-ui`. It is hand-written from `templates/component/` in `components/NavBar/`, so no generated public component remains: generated components back the Review previews only. Its open limits are recorded in the [component adoption tracker](../../docs/ui-components.md). Component deep imports remain unavailable.

The NavBar header is 64px below the 1024px desktop breakpoint and 80px at and above it. Header slot controls must fit within a 48px block size; applications own their labels, intrinsic widths and popup positioning outside normal flow. The header preserves control hit areas and focus outlines without clipping, scaling or reducing them. Larger content requires a separate layout contract rather than relying on header growth.

The design values are generated from the verified capture pinned by `upstream.lock.json`, preserving its Dark semantic mode and four responsive layout modes. These outputs do not certify parity with later live design changes. The five families use four source pages: Colors (`1:5238`), Icons (`1:5239`), Typography (`1:5237`) and Layout & Spacing (`15521:20146`, shared by layouts and spacings). No live source is written into the library.

`semantic` exposes resolved Dark-mode values for inspection. Use `theme.color` for semantic CSS references. A text style's `fontSize` references the responsive CSS variable; `fontSizePx` is the captured tablet-and-larger value for responsive headings, not the current viewport measurement. Use the generated CSS classes for rendering and computed styles for viewport-specific pixel measurements.

Consumers configure `@dcl/one-ui` and its CSS subpaths in their TypeScript and bundler aliases before importing this source library. Application adoption, including alignment of existing Inter font registrations, is separate from this package.

Inter variable normal faces (weights 100–900) come from `@fontsource-variable/inter` 5.3.0 under the SIL Open Font License in `foundations/typography/fonts/OFL.txt`. `foundations/typography/font-source.json` pins their materialized payloads; Git LFS stores the WOFF2 assets. Font ownership is independent of the Figma capture. Do not remove the font faces or replace them with a network font dependency.

Monochrome icons inherit `currentColor`, and active-state pairs expose `active`. Icons preserve their captured intrinsic dimensions unless `size` is supplied. Give informative icons an accessible name with SVG attributes such as `role="img"` and `aria-label`; mark decorative icons `aria-hidden="true"`. Skipped source records are listed in `skippedIcons` rather than silently substituted.

## Button

Import `Button` and `ButtonProps` from `@dcl/one-ui`. Without `href` it renders a native button (`type="button"` by default); with `href` it renders an anchor and forwards cancellable native events. Links targeting a new or named browsing context retain the supplied `rel` tokens and add `noopener noreferrer`, including case-insensitive special targets.

Use `children` or `label` for content, `leadingIcon` and `trailingIcon` (also `startIcon` and `endIcon`) for decorative icons, and `className` for consumer geometry. `variant="iconOnly"` or `iconOnly` requires `aria-label` or `aria-labelledby` in the public type. Supply content or an accessible name explicitly; the public control never supplies specimen text. Native button and anchor refs are typed. Native `disabled` prevents focus and activation; `aria-disabled` keeps the control focusable with disabled visuals while suppressing click and auxiliary activation. `loading` retains the content and accessible name with a decorative busy indicator, marks the control busy, retains keyboard focus and prevents repeated activation. Both button and link controls accept these states.

Captured variants remain `primary`, `secondary`, `outline`, `dark`, `text` and `outlineOnLight`. Public aliases `tertiary` and `quaternary` select `outline` and `dark`. The white `inverse` appearance and the neutral `iconOnly` appearance are explicit library additions. Desktop heights are `xl` 56px, `lg` 48px, `md` 40px and `sm` 32px; mobile heights are 56px, 52px, 48px and 44px respectively. The defaults are `xl` and `viewport="desktop"`. Icon-only controls have a 48px minimum target.

## Work on it

Node 24 and pnpm (`corepack enable`). The Figma capture is not in this repository: it lives in [figma-design-system](https://github.com/decentraland/figma-design-system) (FDS). `upstream.lock.json` pins two FDS commits: `revision`, the code base every ported file is compared against, and `snapshot.revision`, the capture `fetch-source` reads, with its digest table.

```sh
cd library/ui
git lfs pull --include "library/ui/foundations/typography/fonts/*.woff2"
pnpm install --frozen-lockfile
pnpm format:check && pnpm lint && pnpm typecheck && pnpm test
node figma/lock-digests.mjs  # ported tooling, foundations and installed components match pinned bytes and origins
pnpm review                  # Review gallery on http://localhost:6019/dcl-ui-review/
pnpm review:build --base <BASE>  # static Review; BASE is / (default), ./, or an absolute nested prefix
pnpm review:check-build      # the built gallery navigates and renders in Chromium
```

## The capture lives in figma-design-system

The Review is a gallery of the generated components only. It publishes no Figma imagery: no reference screenshots, no fidelity comparison and no exported image fill (image fills render as a neutral placeholder). Comparing generated output with the real capture is done where the capture lives, so the guard is split in two halves:

- **In every pull request here** (public, no credential): `lock-digests.mjs` fails when any tracked file under `figma/` differs from, is missing from, or is not pinned in `upstream.lock.json`. Each pinned file also records its figma-design-system counterpart, and a file that differs from it, or has none, must name deviation codes from `deviationCodes`, each mapped to its reason under a stable id, in sorted order (the code `note` maps to null and the file carries a short `note` instead). Nothing under `figma/` changes without a lock change.
- **When a port input changes**: `port-verification.mjs` requires `port-verification.json`, the record of the real-capture checks (`fetch-source`, `deviations`, `diff`, `check-mappings`, `review-manifest`, `navbar-bounds`, `install`), all passed, for exactly these port inputs: the lock except its provenance text (license, imported paths, narrative changes, deviation reasons, per-file notes) and every tracked file under `figma/` except tests, test fixtures and Markdown. Exempt files keep their lock entry and FDS counterpart bound. A changed port input without a matching record fails; it is never skipped. Pull requests that only edit existing tests, fixtures, the skills or maintenance notes need resealed digests and no new record. The record states what a local run reported; CI checks that it names these inputs and that every check says `pass`, not that the checks ran, and it is not an attestation or evidence of live Figma parity ([ADR](../../docs/adr/2026-11-10-port-verification-binds-port-inputs.md)).

Maintainers with access to FDS run those checks locally:

```sh
pnpm figma fetch-source      # materialize the pinned capture into the gitignored figma/figma-snapshot/
pnpm figma diff              # generated output matches the capture (exit 1 if not)
pnpm figma check-mappings    # every *.figma.ts matches the library and the capture
```

`fetch-source` fetches exactly the pinned commit over SSH into a temporary repository, rewrites each file into the keyless form this tree reads, and accepts it only when every file matches the digest table in the lock and every ported file's recorded counterpart matches the pinned commit; the raw objects are deleted before it returns. Every command that reads the capture fails, naming `pnpm figma fetch-source`, when the cache is missing, stale or edited. A port bumps the pinned revision, runs `pnpm figma fetch-source --seal`, stages `library/ui` and runs `node figma/lock-digests.mjs --write` (it reads the index), runs the checks above and commits their record. Promotion and the fidelity evidence belong to FDS.

## The Figma file key is private

The key of the Figma file never enters the repository, a generated file, a log or an artifact.

- Live Figma access is for local inspection only: `diff --source rest`, the MCP read tools with `source: "rest"`, `figma_screenshot` (the PNG is returned to the caller, never written) and `probe` read the live file with `FIGMA_TOKEN` and `FIGMA_FILE_KEY` from the environment only. Shipped output comes from the pinned capture only: `sync` and every command that writes tracked files read the verified fetch-source cache and refuse the live source. No CI job runs live code. The key is never printed: errors redact it, and the key guard (`key-guard.mjs`) scans for leaks; without the variable its `key` check reports SKIPPED while the URL checks still run.
- Snapshot ingest and `fetch-source` drop `fileKey` fields and Figma file URLs; API errors and reports redact the key.
- Mappings name the file as `<DCL_FIGMA_FILE>`; Code Connect resolves it with `documentUrlSubstitutions` at publish time only, outside this tree's code.
- `make figma-key-guard` (or `node library/ui/figma/key-guard.mjs`) fails when the key (`key` check, needs `FIGMA_FILE_KEY`) or any Figma file URL (`url` check) is in the working tree, in a blob of `origin/main..HEAD`, or in a directory passed with `--path`. It prints paths and check IDs only. Run it before every commit and push; CI runs it on every pull request and before every artifact upload. `figma/key-guard-allow.json` pins pre-existing public URLs by path and Figma file id, so any other URL added to those files still fails; the `key` check cannot be allowlisted.
- The privileged key scan (`ui-library-key-scan.yml`) reads the URL allowlist from the default branch, never from the scanned commits, so a pull request that adds a public Figma URL together with its `key-guard-allow.json` entry fails that scan until the entry lands on main.

## From Figma to the Review

This pipeline feeds the Review previews; public components come from the component template instead.

1. **Capture**: in figma-design-system, which owns the capture, its visual evidence and the fidelity review ([`figma/MAINTENANCE.md`](figma/MAINTENANCE.md)). This tree reads it through `pnpm figma fetch-source`.
2. **Generate** (`pnpm figma sync`): Review previews in `figma/review/src/generated/`. Never edit them by hand.
3. **Review**: `pnpm review:build` and `pnpm review:check-build` prove the gallery builds and renders; visual comparison with Figma happens in figma-design-system.
4. **Promote**: the promotion seal, its verification and `promote-reviewed` belong to figma-design-system; this tree keeps only the eligibility rule `check-mappings` reports (`figma/src/promotion/eligibility.ts`).

A synced component with the name of a hand-written one (NavBar) replaces it only when `promotion.include` names it explicitly (promotion, in figma-design-system, then deletes the hand-written directory and its exports; as a preview dependency or through the all-eligible default, the same name fails promotion). Once `promotion.include` names it, `check-mappings` reports the hand-written mapping as `superseded-by-sync` (eligible) or `superseded-pending` (with the reasons promotion still skips it) instead of validating it; until then the hand-written mapping is validated as usual, even when a ready page generates an eligible component with its name. Name a hand-written component in `promotion.include` only after every consumer works with the synced API.

Two registries decide different things and stay separate. `promotion.include` in `figma/figma.config.json` names the synced components promotion writes; it never names a hand-written public component. `components/promotion.json` decides what `pnpm figma install components` installs and whether each installed component is public (mapped and exported) or internal.

Generated views reproduce the reviewed design for the Review; they do not implement production keyboard, focus or navigation semantics, which public components implement and test.

Generated styles use three cascade layers, declared in this order at the top of every generated stylesheet: `dcl.reset` (the runtime's base styles), `dcl.foundations` (tokens and text styles) and `dcl.components` (component styles). The cascade decides between them whatever order a bundle loads the files in, and a consumer's unlayered CSS overrides all three.

Font contract: text styles name Inter. Faces are provided by the consumer: the Review app loads `@fontsource/inter` (400/600/700); library consumers get them from the foundations stylesheet, except the web apps (`apps/sites`, `apps/ui3`), which load the token sheets and declare Inter v20 themselves (`docs/ui-standards.md`, Integration). Promotion never removes a foundations stylesheet, its font stylesheet or font files. `figma/review/test/runtime-cascade.test.ts` checks in Chromium that the Review's generated NavBar preview draws its label with the loaded Inter web font under both stylesheet orders.

A generated component throws during render when it receives a variant combination Figma never drew, which only an untyped caller (plain JavaScript, spread props) can pass. The error names the component and every axis value, for example, from the Review's generated NavBar preview, `NavBar has no captured view for viewport="largeDesktop", balances="credits", theme="dark", signedIn=false`. This is decided by the owner: throw in all environments, server rendering included; there is no fallback view. A consumer that renders generated components from data it does not type-check should place them under a React error boundary, and let server rendering surface the error through the route's error handling (for example a framework `ErrorBoundary` route export) instead of catching and hiding it.

`figma/figma.config.json` can bind named text roles to captured text layers (`components.<Figma name>.textRoles`): each role is a public prop bound by Figma node id, and each node states its expected path of layer names, so generation fails on an unknown id or a renamed path instead of binding the wrong text. A `string` role takes text. A role whose text sits inside a linked action declares that link's prop name with `href` (for example `"discoverLabel": { "type": "string", "href": "discoverHref", ... }`): the generator emits exactly that name, and generation fails if it is missing or two roles declare the same one. A `count` role takes a non-negative integer and needs its `label` role together with it; the component throws on any other count value or a missing label. The label becomes the accessible name of the action around the count and replaces its captured name, so it must state the count itself, localized by the consumer (for example `notificationCount={12}` with `notificationsLabel="12 notifications"`). Binding needs node ids in the capture, which the current capture does not record yet, so no component binds roles today.

`components.<Figma name>.responsive` makes a variant axis follow the foundations breakpoints (`foundations/layout`, from the Layout collection's `layout/breakpoint-min`): `{ "prop": "viewport", "breakpoints": { "mobile": "mobile", "desktop": "desktop", "largeDesktop": "largeDesktop" } }` maps each option of the prop to a breakpoint. Generation fails on an unknown prop or breakpoint, an option without a breakpoint, two options on one breakpoint, a narrowest option above 0px, or an option missing a combination of the other axes that another option draws. The generated component gives that prop no default: a caller that omits it gets every option's view, and generated media queries show each one from its breakpoint's minimum width up to the next (the Review's NavBar preview: `mobile` below 1024px, `desktop` from 1024px, `largeDesktop` from 1536px), so server rendering and hydration produce the same markup and nothing reads the window. The hiding rule is `!important`, so a consumer's `display` cannot show two views at once. Passing the prop renders exactly one view, as before. Without it, every view carries the caller's attributes, so a `data-testid` or an `aria-*` relation appears once per view; an `id`, a `ref` or a Review disclosure names one element, so the component throws when one is given without the prop. An undrawn combination of the other axes throws from the narrowest option, so the error names that option's value (for example `viewport="mobile"`).

## Provenance

`upstream.lock.json` records the imported sources, their revisions and licenses, the digest of every ported file and of every file of the pinned capture.

This tree ships the pinned `9c6dfbe6` capture. Reported live differences in colors (89 primitives and 42 semantics), text styles (34 rather than 32), spacing (18 rather than 16) and body/sm line height await a coordinated capture refresh. They are not included until the capture is refreshed and foundations are regenerated.

### Regenerate foundations

Maintainers run `pnpm figma fetch-source` to materialize the pinned cache, then `pnpm figma install foundations`. This single install boundary regenerates the five families and `source.json`, preserves maintained CSS and licensed assets, and refuses unverified input or dirty targets. For an isolated reproduction, use `pnpm figma install foundations --out ../.agent-work/figma-install/proof/foundations`. Repeating installation makes no changes.

The same command installs the internal and public names in `components/promotion.json`: `pnpm figma install components`. The `components` list controls public visibility; `internal` names are installed without a Figma mapping or a package export. The installer refuses duplicate or unknown names, binds configuration, registry, locked runtime, generator modules, the committed retirement ledger and dependency files before planning, then rechecks those inputs before its atomic publication. An empty registry installs only its name list and generation record, removing retired component and runtime files through the same transaction. Use `--out ../.agent-work/figma-install/proof/components` for a private reproduction. Component installation writes `generation.json` from the emitted plan, and the public component table in the lock pins those bytes and their origins. `node figma/lock-digests.mjs --write` rewrites that table, and the foundation table, from the staged manifests, so a reinstall needs no hand-edited digest. A component written from `templates/component/` is a top-level directory the table does not name: the lock does not pin it, and `lock-digests` refuses it when it is untracked or not TypeScript or CSS, or holds an LFS pointer, a Figma URL or key-shaped value, or a known generator marker (the generator header, an import of the generated `runtime/`, `registerComponent` or `FigmaView`, a `// Figma: … (n:n)` node comment). A known marker is a heuristic, not proof that a file was written by hand. The table pins `generation.json` by digest. That record's module list is the installer's read-set: the fixed inputs, every module the install process loads (the static import closure of `figma/src/install-main.ts`, recomputed by the offline guard and failing closed on any import it cannot resolve) and any non-code file under `figma/src`; each is validated against its digest in the source lock, and output origins do not repeat the list. Tooling outside that set (the resolver, other CLI commands, the MCP server, the port commands, the guards) is not a generation input, so editing it needs resealed lock digests but no new component install ([ADR](../../docs/adr/2026-11-11-generation-binds-installer-import-closure.md)). The offline guard checks byte and module consistency, not live design parity. Structural resolver checks refuse additional package scopes and local dependency lookup roots without requiring installed packages. The installer additionally checks dependency resolution against the sanctioned UI installation before publication; installed dependency contents remain trusted execution inputs, and these checks do not sandbox initial module evaluation. Stylesheet declarations use the same CSS Modules parser as the build, including composed styles, escaped selectors, global selectors and animation exports. No generated public component remains: NavBar is hand-written, so the registry is empty and the components target installs only its name list and generation record.

The installer owns files, not directories: it removes or overwrites only `generation.json`, `promotion.json` and an output the lock's public table or the installed `generation.json` pins, while its bytes match that pin. Every other file in a component directory, including a committed edit over a generated file, is carried over byte for byte; a plan that would write over such a file, or into a component directory that holds one, is refused with the file's name, and so is an unowned file at the top of `components/`. To move an installed component to hand-written, remove its name from `components/promotion.json` and from `promotion.include` in `figma/figma.config.json` (remove the whole `promotion` block when it was the only name: the schema refuses an empty `include`), and commit. Run `node figma/lock-digests.mjs --write`: until the lock is resealed with the new configuration digest, the installer refuses `Unverified component input: figma.config.json`. This run exits 1 and keeps the public component table, which still names the component, until the reinstall. Run `pnpm figma install components`, stage `library/ui`, run `node figma/lock-digests.mjs --write` again so the public table stops naming the component, commit, and run `pnpm figma port verify`. Hand-written files can be committed before or after the install: one the installer never listed (such as `NavBar/NavBar.test.tsx`) or one whose bytes differ from the generated output it replaces (such as a hand-written `NavBar/NavBar.tsx`) stays.
